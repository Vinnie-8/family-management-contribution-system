    Feature: Authentication — Entity-Relationship Diagram & Build Notes

    feature/auth is complete: identity, Chairman-issued onboarding, login, roles, and the audit-log foundation every later branch builds on.

    Introduction

    Every feature in this system — campaigns, pledges, payments, meetings, reports — depends on one question being answered first: who is doing this, and are they allowed to? feature/auth exists to answer that question properly, once, in a way every later branch can simply rely on rather than re-solving.

    This isn't open self-registration. The family already has real, existing governance — a Chairman, a Secretary, a Treasurer — and the system is built to work the way the family actually operates, not to replace it with a generic sign-up form. A member never creates their own account. Membership is issued, deliberately, by someone with the authority to issue it, the same way it would be in a real family meeting: the Chairman says who's in, and the system reflects that decision rather than second-guessing it.

    The feature covers five things, each building on the one before it: the family itself as the root of the whole system, the people who belong to it, the roles those people can hold, the credentials that let them prove who they are, and an immutable record of everything that happens along the way. Nothing in this feature is throwaway scaffolding — every table, every constraint, every security decision here is the floor the other twelve feature branches stand on.

    The Flow — from organization to active member

    It starts with the family itself. In this system, a family is the organization — the single tenant the whole platform serves. That root record is established once, holding nothing more than a name and a creation timestamp, and everything else in the database — every member, every campaign, every payment — ultimately traces back to it through a family_id. The schema is built so that supporting more than one family later is possible without a redesign, but v1 deliberately runs with exactly one: this isn't a multi-tenant SaaS product yet, it's one real family's system, built properly from day one.

    Once the family exists, someone has to be its first Chairman — the person whose authority everything else flows from. From that point on, onboarding a new member is entirely the Chairman's (or Secretary's) action, not the member's own. The Chairman fills in a new member's basic details — their name, and at least a phone number or an email, so there's somewhere to actually deliver their credentials — and submits it. Nothing about this request mentions which family the new member belongs to; that's deliberately never something the caller gets to choose. It's taken directly from the Chairman's own session, so there's no path by which anyone could onboard a member into a family that isn't theirs.

    The moment that request lands, the system generates a temporary password — a short, random string built to avoid characters that look alike on a small phone screen, since this is often read off an SMS by someone who isn't especially comfortable with technology. That password is hashed immediately, the same way any real password would be, and the plain version is never written to the database at all — it exists only long enough to be handed off for delivery, and then it's gone. Alongside it, the system marks this member as needing to change their password before doing anything else, and sets a 48-hour clock on how long that temporary credential is allowed to remain valid.

    The new member receives that password — today, as a line printed to a console standing in for a real SMS gateway that doesn't exist yet, but written so that swapping in a real one later changes nothing about how onboarding itself works. They log in with it, and the system checks, in order: does this person actually exist, is their account active, has the 48-hour window already closed, and does the password they typed actually match what was issued. If all of that holds, they're let in — but not all the way in. Because this is still a temporary password, every part of the system except the "change your password" action is closed to them. They can't view a campaign, can't make a payment, can't do anything else, until they've replaced it with something only they know.

    Changing it is itself a small, deliberately careful step — the member has to prove they still know the temporary password before they're allowed to replace it, even though they're already holding a valid session token. That's not redundant; it's what stops a stolen token alone from being enough to lock the real member out of their own account. Once the new password is set, the temporary one is gone for good, the forced-change flag clears, and the member is sent back to log in fresh — this time with full access, shaped by whatever roles the Chairman has assigned them.

    And every single step along that path — the family's creation, the onboarding, the first login, the password change — leaves a permanent, unchangeable trace: who did it, what changed, and when. Not as an afterthought bolted on at the end, but as part of the same action, inside the same transaction, from the very first branch of this project onward.

    What's inside feature/auth

    • Five database tables

      Family, Member, Role, MemberRole, AuditLog — with foreign keys, unique constraints, and check constraints enforcing the rules above at the database level, not just trusted to application code.

    • Password security

      bcrypt hashing for every password, temporary or permanent; cryptographically secure random generation for temporary passwords.

    • Session handling

      JWT-based access tokens, signed with a secret kept out of version control.

    • A universal active-account gate

      checked in exactly one place, so a deactivated member is blocked from everything the instant that happens, with no risk of a forgotten endpoint that never learned to check it.

    • Role-based access control

      evaluated as the union of a member's roles, since one person can legitimately hold several at once.

    • A clean separation of layers

      database models, security primitives, business logic, request validation, and HTTP endpoints each live in their own place, so the same logic could be reused outside a web request if it ever needed to be.

    • An audit trail from the first commit

      not retrofitted later, but built in from the very first feature, so every later branch inherits the same discipline automatically.

        boolean is_active

        uuid id PK
        string name UK
        string description
    }

    MEMBER_ROLES {
        uuid id PK
        uuid member_id FK
        uuid role_id FK
        datetime assigned_at
    }

    AUDIT_LOGS {
        uuid id PK
        uuid family_id FK
        uuid actor_member_id FK
        string action
        string entity_type
        uuid entity_id
        jsonb before_state
        jsonb after_state
        datetime created_at
    }

    Five entities, two deliberate design choices worth highlighting:

    • MEMBER_ROLES is a junction table, not a single role_id column on MEMBERS — because role assignment is many-to-many (a Chairman can also be a contributing Member). A single foreign key can only ever point at one role; the junction table is what lets a member hold several roles at once.
    • Minors are MEMBERS rows too, not a separate table — is_minor is a flag, with phone_number/email/hashed_password left NULL. This keeps every other relationship that points at a member (future Pledge, Payment, Attendance tables) working unchanged for minors, with no parallel structures needed.

    How it was built — layered, bottom to top

    flowchart TD
    A["models/ — SQLAlchemy ORM<br/>5 tables, constraints, relationships"] --> B["Alembic migration<br/>generated & applied to Postgres"]
    B --> C["core/ — security, exceptions, permissions<br/>password hashing · JWT · RBAC"]
    C --> D["services/ — business logic<br/>audit_service · auth_service"]
    D --> E["schemas/ — Pydantic validation<br/>request/response contracts"]
    E --> F["routers/ — HTTP endpoints<br/>/auth/onboard · /auth/login · /auth/change-password"]

    Each layer only depends on the one below it — routers knows about schemas and services, but services never imports FastAPI at all. That separation is what lets the same auth_service.onboard_member() function be called from a web request today, and from a CLI script or background job later, with zero changes.

    The onboarding → login → forced change flow

    sequenceDiagram
    participant C as Chairman
    participant R as Router
    participant S as auth_service
    participant DB as Postgres

    C->>R: POST /auth/onboard
    R->>S: onboard_member()
    S->>S: generate temp password, hash it
    S->>DB: INSERT member (must_change_password=true)
    S-->>C: temp password "sent" via SMS stub

    Note over C: Member logs in with temp password

    C->>R: POST /auth/login
    R->>S: authenticate()
    S->>DB: verify is_active, password hash, expiry
    S-->>C: access token (must_change_password=true)

    Note over C: Restricted to change-password only

    C->>R: POST /auth/change-password
    R->>S: change_password()
    S->>DB: UPDATE hashed_password, clear flags
    S-->>C: success — must log in again

    Security measures built into this feature

    • Passwords are hashed with bcrypt, never stored in plain text — not even the temporary one.
    • JWT-based sessions, signed with a secret key kept out of version control (.env, gitignored).
    • is_active is checked in exactly one place — the point a token resolves back to a member — so a deactivated member is blocked from everything the instant Chairman flips the switch.
    • Role-based access control evaluates the union of a member's roles, not a single assumed role, since one person can hold several.
    • Database-level CHECK constraints back up application-level validation — e.g. an adult member must have a phone or email, enforced by Postgres itself, not just trusted to the API layer.
    • Every onboarding, login, and password change writes an immutable audit log entry — actor, action, before/after state, timestamp.

    What's deliberately deferred

    • Real SMS delivery — send_sms() is a stub that logs to console; swapping in a gateway later requires no change to the code.
